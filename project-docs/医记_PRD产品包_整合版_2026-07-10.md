# 医记 PRD：上线网页 MVP

**版本**：MVP / V1.0 产品定义稿  
**日期**：2026-07-10  
**状态**：Draft  
**产品形态**：已上线的移动端优先响应式网页  
**核心原则**：隐私优先  

## 1. Executive Summary

医记是一款帮助患者本人管理病历和药物的网页产品。它解决的核心问题是：用户的病历、检查报告、处方、用药记录和就诊资料散落在相册、纸质文件、医院网站和不同平台里，真正看病时很难快速整理成一份医生能看懂的资料。

本版本的目标不是做 AI 医生，也不做 OCR 自动识别，而是先把“手动上传、分类整理、日常维护、就诊前生成完整资料包”的闭环跑通。成功标准是：用户在一次就诊前，可以生成一份完整、可导出的就诊资料包。

## 2. Background & Context

旧版文档中，医记曾包含 OCR、AI 归类、摘要生成、药品扫描等能力。但当前产品决策明确：MVP 暂不引入 AI/OCR，因为识别能力不稳定且医疗场景风险高。

因此，新版 PRD 将产品重心调整为：

- 用户自己上传原始资料。
- 用户自己填写或核对结构化字段。
- 系统负责安全保存、分类、搜索、时间线、提醒和导出。
- 所有医疗事实必须可追溯到用户录入或原始资料。
- 产品不提供诊断、治疗建议、药品替代建议或剂量调整建议。

旧版 V1.3 的主线仍然保留：

```text
建档 -> 补全 -> 维护 -> 就诊使用
```

但其中“AI 识别”改为“用户手动录入 / 用户核对归档”。

## 3. Objectives & Success Metrics

### Goals

1. 让患者本人能够把散落在不同医院网站、相册、纸质材料中的病历资料集中保存和分类。
2. 让用户能够维护当前用药、健康指标、复查和资料处理待办。
3. 让用户在就诊前选择相关资料，生成一份完整的 PDF 就诊资料包。
4. 建立隐私优先的数据权限、授权、删除和导出机制。
5. 验证订阅会员家庭版是否有付费价值。

### Non-Goals

1. 不做 AI 诊断、疾病概率预测、治疗方案推荐。
2. 不做 OCR 自动识别作为 MVP 必需能力。
3. 不自动推荐用药、改变剂量或判断药品替代关系。
4. 不接入医院 HIS、电子病历平台或医保系统。
5. 不做医生工作台、问诊社区、药品交易或导流问诊。
6. 不默认允许家庭成员读取成年人的病历，必须经过明确授权。

### Success Metrics

| Metric | Current | MVP Target | Measurement |
|---|---:|---:|---|
| 首次建档完成率 | 待测 | >= 70% | 登录后完成本人档案 |
| 首份病历上传完成率 | 待测 | >= 60% | 建档后 24 小时内上传至少 1 份资料 |
| 首次归档时间 | 待测 | <= 3 分钟 | 从上传到完成分类归档 |
| 就诊资料包生成成功率 | 待测 | >= 50% | 上传资料用户中生成资料包比例 |
| 资料包可用性 | 待测 | 用户认为“能直接给医生看”>= 70% | 封闭测试问卷 |
| 第二份资料上传率 | 待测 | >= 25% | 30-60 天内再次上传 |
| 用药提醒使用率 | 待测 | >= 20% | 创建药品且设置提醒 |
| 订阅转化率 | 待测 | >= 3% | 试用用户转家庭订阅 |

### Data Instrumentation

MVP 必须同步建设最小埋点能力，否则无法判断产品是否跑通。第一批埋点以核心闭环为准：注册、建档、上传、归档、药品、指标、待办、资料包创建、PDF 导出、数据导出、删除请求。

埋点不得采集病历正文、药品名称、诊断名称、医院名称原文、指标具体数值、原始搜索词、文件 URL、分享 token、验证码、Cookie 或访问令牌。详细方案见 `医记_数据指标与埋点方案_2026-07-10.md`。

## 4. Target Users & Segments

### Primary User

患者本人。

### Initial Segment

20-45 岁、有跨医院就诊、体检、慢病复诊或长期用药经历的用户。他们能独立使用网页、邮箱验证和文件上传，也更可能为家庭版订阅付费。

### Secondary Users

- 替父母整理病历和药物的子女。
- 替孩子管理病历、用药和复查的父母。
- 慢病患者或长期复查人群。

MVP 以患者本人为第一优先用户，家庭成员能力保留，但不得压过本人闭环。

## 5. Core User Journey

```text
邮箱验证登录
-> 创建本人健康档案
-> 上传病历、检查报告、处方或其他资料
-> 选择资料类型、医院、日期、关联问题和所属成员
-> 添加当前用药和服药提醒
-> 记录关键指标
-> 创建复查、用药、资料补全等待办
-> 通过搜索或时间线持续维护
-> 就诊前选择相关资料
-> 补充本次就诊目的和近期情况
-> 生成并核对就诊资料包
-> 导出 PDF
```

## 6. Requirements

### P0 - Must Have

| # | Requirement | Acceptance Criteria |
|---|---|---|
| P0-1 | 邮箱验证登录 | 用户可通过邮箱验证码注册/登录；验证码不在生产环境明文展示；可退出登录 |
| P0-2 | 本人健康档案 | 用户首次进入后创建本人档案；至少支持姓名/昵称、性别、出生年月、过敏史、长期疾病 |
| P0-3 | 家庭成员管理 | 支持创建家庭成员并切换；每份资料必须归属于一个成员；默认以本人为主 |
| P0-4 | 病历上传 | 支持图片、PDF、常见文档上传；保存原始文件；记录文件名、类型、上传时间、所属成员 |
| P0-5 | 病历分类 | 用户可手动选择资料类型、就诊日期、医院/机构、科室、健康问题标签 |
| P0-6 | 搜索 | 支持按成员、资料类型、医院、日期、关键词搜索 |
| P0-7 | 时间线 | 按成员展示就诊和资料时间线；支持按类型筛选 |
| P0-8 | 用药管理与提醒 | 支持药品名称、规格、用途备注、用法用量原文、开始/结束日期、提醒时间 |
| P0-9 | 指标记录 | 支持体重、血压、血糖、心率、体温；每条指标必须有日期和来源 |
| P0-10 | 待办事项 | 支持复查、用药、资料补全、资料核对等类型；可完成/延期 |
| P0-11 | 就诊资料包 PDF | 用户选择成员、就诊目的、相关资料和近期情况后生成 PDF |
| P0-12 | 隐私授权 | 敏感健康信息处理、家庭成员访问、导出和分享需要明确授权记录 |
| P0-13 | 数据导出与删除 | 用户可导出结构化数据和原始文件；可删除单份资料；可申请账号注销 |
| P0-14 | 安全审计 | 登录、上传、查看、修改、删除、导出、授权等关键操作写入审计 |
| P0-15 | 数据埋点 | 支持核心闭环漏斗、PDF 导出成功率、错误码和隐私相关操作分析；不得采集医疗正文和直接身份信息 |

### P1 - Should Have

| # | Requirement | Acceptance Criteria |
|---|---|---|
| P1-1 | 指标趋势 | 支持按指标查看简单趋势图和异常备注；不做医学判断 |
| P1-2 | 药品库存 | 支持剩余数量、存放位置、有效期、低库存/临期提醒 |
| P1-3 | 限时分享链接 | 资料包可生成限时只读链接，支持撤销和访问记录 |
| P1-4 | 家庭成员授权细分 | 支持查看者、协助录入者、管理者等不同权限 |
| P1-5 | 订阅套餐页 | 展示免费版与家庭订阅权益；不得锁死用户已有数据 |

### P2 - Future

| # | Requirement | Notes |
|---|---|---|
| P2-1 | OCR / AI 结构化提取 | 仅在合规、稳定、可追溯后作为可插拔能力 |
| P2-2 | 微信登录 / 微信小程序 | 网页验证成立后再做 |
| P2-3 | 分享口令或短信验证 | 用于高敏感分享 |
| P2-4 | 更多指标类型 | 血脂、尿酸、肝肾功能等 |
| P2-5 | 年度健康资料报告 | 只能做资料整理，不做诊断或建议 |

# 医记 MVP 范围与结果型路线图

## MVP Scope

### MVP 一句话

医记 MVP 要让患者本人把散落的病历和药物资料整理成一个隐私优先的个人健康档案，并在就诊前生成完整 PDF 资料包。

### In Scope

- 邮箱验证码登录。
- 本人健康档案。
- 家庭成员创建和切换。
- 病历/检查/处方/图片/PDF 上传。
- 手动分类归档。
- 搜索和时间线。
- 当前用药和用药提醒。
- 基础指标记录。
- 复查、用药、资料补全、资料核对待办。
- 就诊资料包 PDF。
- 隐私授权、数据导出、资料删除、账号注销入口。
- 家庭订阅会员的基础权益定义。

### Out of Scope

- AI/OCR 自动识别。
- AI 诊断、治疗建议、用药建议。
- 医院系统接口。
- 微信小程序。
- 付费问诊或药品购买。
- 自动健康风险判断。

## Outcome-Focused Roadmap

**Strategic themes**：

1. 就诊前资料可用。
2. 隐私优先的数据可信。
3. 家庭订阅价值验证。

# 医记用户故事与验收标准

**Format**：User Stories  
**Source**：新版 PRD + 旧版医记文档 + 用户确认需求  

## Stories

### Story 1：邮箱登录

**As a** 患者本人，**I want** 用邮箱验证码登录医记，**so that** 我可以安全访问自己的健康资料。

Acceptance Criteria:

- [ ] 用户输入邮箱后可收到验证码。
- [ ] 验证码过期、错误、重复使用时有明确提示。
- [ ] 生产环境不展示测试验证码。
- [ ] 用户可退出当前会话。

Priority: P0 | Effort: M | Dependencies: 邮件服务、会话管理

### Story 2：创建本人健康档案

**As a** 患者本人，**I want** 首次进入时创建本人健康档案，**so that** 后续资料都能归到正确的人名下。

Acceptance Criteria:

- [ ] 首次登录后引导创建本人档案。
- [ ] 必填项尽量少，过敏史和长期疾病可选。
- [ ] 完成后进入档案补全任务页。
- [ ] 后续上传资料默认归属本人。

Priority: P0 | Effort: M | Dependencies: 成员模型

### Story 3：上传病历资料

**As a** 患者本人，**I want** 上传病历、报告、处方、PDF 或照片，**so that** 我不用在各个医院网站和相册里反复查找。

Acceptance Criteria:

- [ ] 支持图片和 PDF 上传。
- [ ] 上传后保存原始文件和文件哈希。
- [ ] 用户可填写资料类型、医院、日期、科室、标签。
- [ ] 上传失败、文件过大、格式不支持时有明确提示。

Priority: P0 | Effort: L | Dependencies: 文件存储、权限鉴权

### Story 4：手动分类归档

**As a** 患者本人，**I want** 手动把资料分类归档，**so that** 即使没有 AI/OCR 也能形成可查的病历库。

Acceptance Criteria:

## 五、数据指标与埋点方案

> 来源文件：`医记_数据指标与埋点方案_2026-07-10.md`

# 医记数据指标与埋点方案

**版本**：MVP Draft  
**日期**：2026-07-10  
**原则**：隐私优先、最小必要、只采集产品决策需要的数据  

## 1. 为什么需要埋点

医记当前最需要回答的不是“用户点击了多少按钮”，而是这些业务问题：

1. 用户是否能完成从注册到首份资料归档？
2. 用户是否理解“手动整理 + 就诊资料包”的产品价值？
3. 用户是否愿意持续维护病历、用药、指标和待办？
4. 用户是否真的在就诊前生成资料包？
5. 家庭成员和订阅是否带来增量价值？
6. 哪些步骤让用户流失、失败或不信任？

因此，MVP 埋点必须围绕业务闭环设计：

```text
访问 -> 注册/登录 -> 本人建档 -> 上传资料 -> 分类归档
-> 添加药品/指标/待办 -> 搜索/时间线查看
-> 生成就诊资料包 -> 导出 PDF -> 留存/订阅
```

## 2. 合规和隐私边界

医疗健康信息属于敏感个人信息范畴。埋点不得采集病历正文、药品名称、诊断名称、检查结果原文、医院名称原文、文件名原文、邮箱明文、身份证号、手机号、原始文件 URL、分享 token、验证码、Cookie、访问令牌。

埋点只允许采集以下类型：

- 匿名或伪匿名用户 ID。
- 成员数量、资料数量、药品数量、指标数量等计数。
- 文件类型、资料类型、操作结果、耗时、错误码等产品行为数据。
- 是否完成某步骤、是否开启提醒、是否导出 PDF 等布尔或枚举数据。
- 经白名单处理的页面、功能、按钮、套餐类型。

### 禁止采集字段

| Category | Examples | Rule |
|---|---|---|
| 病历正文 | 主诉、诊断、检查结论、医嘱原文 | 禁止 |
| 药品敏感信息 | 药品名称、剂量、用法用量原文 | 禁止 |
| 原始资料信息 | 文件名、文件 URL、图片/PDF 内容、分享 token | 禁止 |
| 直接身份标识 | 邮箱明文、手机号、身份证号、姓名 | 禁止 |
| 精确健康数值 | 血压具体值、血糖具体值、体重具体值 | 默认禁止；如确需分析，只采区间或是否填写 |
| 医院/医生 | 医院名、科室名、医生名 | 默认禁止；如确需分析，只采“是否填写” |

### 可采集替代字段

| Need | Do Not Collect | Collect Instead |
|---|---|---|
| 判断上传了什么资料 | 文件名、报告内容 | `record_type`, `file_mime_group`, `file_size_bucket` |
| 判断分类质量 | 医院名、诊断名 | `has_hospital`, `has_record_date`, `has_tags`, `required_fields_completed_count` |
| 判断用药功能使用 | 药品名称、剂量 | `medicine_created`, `has_reminder`, `schedule_frequency_bucket` |
| 判断指标功能使用 | 具体血压/血糖值 | `metric_type`, `has_value=true`, `source_type` |
| 判断资料包可用性 | PDF 内容 | `visit_pack_sections_count`, `included_records_count`, `export_result` |

参考边界：个人信息处理应有明确合理目的、与目的直接相关，并采取对个人权益影响最小的方式；医疗健康信息属于敏感个人信息，应按更高标准处理。正式上线前需由合规律师复核。

## 3. 北极星指标

### North Star Metric

**每月生成过至少 1 次就诊资料包的活跃用户数。**

定义：

```text
Monthly Visit-Pack Active Users =
在自然月内完成 visit_pack_export_succeeded >= 1 的去重用户数
```

为什么不用“上传资料数”作为北极星：

- 上传资料只是中间行为。
- 医记的最终价值是就诊前可用，而不是存文件。
- 资料包能同时验证资料整理、药品、指标、搜索、分类和 PDF 导出是否成立。

### Supporting Metrics

| Metric | Definition | Target |
|---|---|---:|
| 首次建档完成率 | `profile_created / signup_completed` | >= 70% |
| 首份资料归档率 | `first_record_archived / profile_created` | >= 60% |
| 首次归档耗时 | `record_archived_at - record_upload_started_at` | P50 <= 3 min |
| 资料包生成率 | `visit_pack_created / users_with_archived_record` | >= 50% |
| PDF 导出成功率 | `visit_pack_export_succeeded / visit_pack_export_started` | >= 95% |
| 第二份资料上传率 | 30-60 天内上传第 2 份资料用户占比 | >= 25% |
| 用药提醒使用率 | `medicine_reminder_enabled / medicine_created` | >= 20% |
| 家庭成员创建率 | 创建 >= 2 个成员的活跃用户占比 | >= 15% |
| 试用转订阅率 | `subscription_started / trial_started` | >= 3% |

## 5. Event Naming Rules

使用动词过去式或明确状态：

```text
domain_object_action
```

Examples:

- `auth_code_requested`
- `signup_completed`
- `profile_created`
- `record_upload_started`
- `record_upload_succeeded`
- `record_archived`
- `visit_pack_export_failed`

禁止使用含糊命名：

- `click_button`
- `submit`
- `page_event`
- `ai_success`

## 10. Implementation Recommendations

### Client vs Server

前端埋点适合采集：

- 页面进入。
- 表单开始。
- 用户点击入口。
- 前端校验失败。

后端埋点必须采集：

- 登录成功/失败。
- 上传成功/失败。
- 归档成功。
- PDF 导出成功/失败。
- 授权、撤销、删除、导出。
- 支付/订阅。

核心业务指标以后端事件为准，前端事件只能辅助分析流失。

### Event Pipeline

MVP 可以先用数据库表或轻量事件表：

```text
product_events
- id
- event_name
- user_id_hash
- anonymous_id
- session_id
- properties_json
- occurred_at
- received_at
- environment
```

要求：

- 所有 properties 进入白名单校验。
- 丢弃禁止字段。
- 对邮箱等身份标识只保存哈希或不保存。
- 服务端补充 `received_at`。
- 失败事件也要记录，但只记录错误码，不记录请求正文。

### Error Codes

错误码必须标准化，便于分析：

```text
AUTH_CODE_EXPIRED
AUTH_CODE_INVALID
AUTH_RATE_LIMITED
UPLOAD_FILE_TOO_LARGE
UPLOAD_TYPE_UNSUPPORTED
UPLOAD_STORAGE_FAILED
RECORD_PERMISSION_DENIED
PDF_RENDER_FAILED
EXPORT_PERMISSION_DENIED
DELETE_TASK_FAILED
PAYMENT_FAILED
```

## Fast-Follow Tigers

| # | Risk | Likelihood | Impact | Planned Response | Owner |
|---|---|---:|---:|---|---|
| 1 | 没有 OCR 导致录入成本高 | High | Medium | 优化手动分类表单；常用字段默认值；后续评估 OCR |

## Paper Tigers

- “没有 AI 就没有价值”：不成立。当前核心价值是安全集中保存、快速查找和就诊前资料包。
- “必须先做 App”：不成立。网页足够验证上传、整理、导出和订阅意愿。
- “功能少用户不会付费”：未必。若资料包解决真实就诊痛点，家庭版仍可验证付费。

## Elephants in the Room

1. 旧版文档和原型里 AI/OCR 承诺较多，必须主动降级，否则用户预期会错位。
2. “中国大陆用户”与现有 Vercel/Resend 等服务之间可能存在长期生产适配问题，需要明确当前只是验证还是公开商业化。
3. 医疗健康数据合规成本高，不能等到用户量起来后再补权限、删除、审计和备案。

## Data Permission Baseline

### Principles

- 默认拒绝。
- 每份病历、药品、指标、待办、资料包都必须有 `member_id`。
- 后端根据资源真实归属鉴权，不接受前端声明的成员归属。
- 成年成员资料必须主动授权。
- 客服和后台默认无权读取病历正文和原文件。
- 删除、导出、授权、分享都必须写审计。

### Roles

| Role | Scope | Allowed |
|---|---|---|
| SELF | 本人档案 | 完整控制本人资料 |
| GUARDIAN | 未成年人档案 | 管理未成年人资料 |
| MANAGER | 获授权家人 | 管理资料、药品、提醒；导出/删除需配置 |
| CONTRIBUTOR | 协助录入者 | 上传和修改资料，不能导出或分享 |
| VIEWER | 只读家人 | 查看授权范围，默认不能下载原件 |
| SUPPORT | 客服 | 默认无医疗资料权限 |

### MVP Privacy Center

- 查看隐私政策和服务协议。
- 查看敏感健康信息处理说明。
- 导出结构化数据和原文件。
- 删除单份资料。
- 撤销家庭授权。
- 注销账号入口。
- 查看第三方服务清单。

## Key Product Decisions Captured

- MVP 不做 AI/OCR，避免医疗风险和识别质量风险。
- 旧版“就医摘要”升级为“就诊资料包 PDF”。
- 首页应围绕“今日”和“我要去看医生”，不是泛泛 Dashboard。
- 患者本人闭环优先，家庭版订阅作为下一阶段验证重点。
- 中国大陆用户和敏感健康数据合规是正式公开前的硬约束。
- MVP 必须有最小数据埋点，否则无法判断首份资料归档、资料包 PDF 和家庭订阅是否成立。
