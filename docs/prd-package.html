一、主 PRD

来源文件：医记_PRD_上线网页MVP_2026-07-10.md

医记 PRD：上线网页 MVP

版本：MVP / V1.0 产品定义稿 日期：2026-07-10 状态：Draft 产品形态：已上线的移动端优先响应式网页 核心原则：隐私优先

1. Executive Summary

医记是一款帮助患者本人管理病历和药物的网页产品。它解决的核心问题是：用户的病历、检查报告、处方、用药记录和就诊资料散落在相册、纸质文件、医院网站和不同平台里，真正看病时很难快速整理成一份医生能看懂的资料。

本版本的目标不是做 AI 医生，也不做 OCR 自动识别，而是先把“手动上传、分类整理、日常维护、就诊前生成完整资料包”的闭环跑通。成功标准是：用户在一次就诊前，可以生成一份完整、可导出的就诊资料包。

2. Background & Context

旧版文档中，医记曾包含 OCR、AI 归类、摘要生成、药品扫描等能力。但当前产品决策明确：MVP 暂不引入 AI/OCR，因为识别能力不稳定且医疗场景风险高。

因此，新版 PRD 将产品重心调整为：

  • 用户自己上传原始资料。
  • 用户自己填写或核对结构化字段。
  • 系统负责安全保存、分类、搜索、时间线、提醒和导出。
  • 所有医疗事实必须可追溯到用户录入或原始资料。
  • 产品不提供诊断、治疗建议、药品替代建议或剂量调整建议。

旧版 V1.3 的主线仍然保留：


建档 -> 补全 -> 维护 -> 就诊使用

但其中“AI 识别”改为“用户手动录入 / 用户核对归档”。

3. Objectives & Success Metrics

Goals

  1. 让患者本人能够把散落在不同医院网站、相册、纸质材料中的病历资料集中保存和分类。
  2. 让用户能够维护当前用药、健康指标、复查和资料处理待办。
  3. 让用户在就诊前选择相关资料，生成一份完整的 PDF 就诊资料包。
  4. 建立隐私优先的数据权限、授权、删除和导出机制。
  5. 验证订阅会员家庭版是否有付费价值。

Non-Goals

  • 不做 AI 诊断、疾病概率预测、治疗方案推荐。
  • 不做 OCR 自动识别作为 MVP 必需能力。
  • 不自动推荐用药、改变剂量或判断药品替代关系。
  • 不接入医院 HIS、电子病历平台或医保系统。
  • 不做医生工作台、问诊社区、药品交易或导流问诊。
  • 不默认允许家庭成员读取成年人的病历，必须经过明确授权。

    Data Instrumentation

    MVP 必须同步建设最小埋点能力，否则无法判断产品是否跑通。第一批埋点以核心闭环为准：注册、建档、上传、归档、药品、指标、待办、资料包创建、PDF 导出、数据导出、删除请求。

    埋点不得采集病历正文、药品名称、诊断名称、医院名称原文、指标具体数值、原始搜索词、文件 URL、分享 token、验证码、Cookie 或访问令牌。详细方案见 医记_数据指标与埋点方案_2026-07-10.md。

    4. Target Users & Segments

    Primary User

    患者本人。

    Initial Segment

    20-45 岁、有跨医院就诊、体检、慢病复诊或长期用药经历的用户。他们能独立使用网页、邮箱验证和文件上传，也更可能为家庭版订阅付费。

    Secondary Users

    • 替父母整理病历和药物的子女。
    • 替孩子管理病历、用药和复查的父母。
    • 慢病患者或长期复查人群。

    MVP 以患者本人为第一优先用户，家庭成员能力保留，但不得压过本人闭环。

-> 导出 PDF

    医记 MVP 范围与结果型路线图

    MVP Scope

    MVP 一句话

    医记 MVP 要让患者本人把散落的病历和药物资料整理成一个隐私优先的个人健康档案，并在就诊前生成完整 PDF 资料包。

    In Scope

  • 邮箱验证码登录。
  • 本人健康档案。
  • 家庭成员创建和切换。
  • 病历/检查/处方/图片/PDF 上传。
  • 手动分类归档。
  • 搜索和时间线。
  • 当前用药和用药提醒。
  • 基础指标记录。
  • 复查、用药、资料补全、资料核对待办。
  • 就诊资料包 PDF。
  • 隐私授权、数据导出、资料删除、账号注销入口。
  • 家庭订阅会员的基础权益定义。

    • Out of Scope

  • AI/OCR 自动识别。
  • AI 诊断、治疗建议、用药建议。
  • 医院系统接口。
  • 微信小程序。
  • 付费问诊或药品购买。
  • 自动健康风险判断。

    医记用户故事与验收标准

    Format：User Stories Source：新版 PRD + 旧版医记文档 + 用户确认需求

    Stories

    Story 1：邮箱登录

    As a 患者本人，I want 用邮箱验证码登录医记，so that 我可以安全访问自己的健康资料。

    Acceptance Criteria:

    • [ ] 用户输入邮箱后可收到验证码。
    • [ ] 验证码过期、错误、重复使用时有明确提示。
    • [ ] 生产环境不展示测试验证码。
    • [ ] 用户可退出当前会话。

    Priority: P0 | Effort: M | Dependencies: 邮件服务、会话管理

    Story 2：创建本人健康档案

    As a 患者本人，I want 首次进入时创建本人健康档案，so that 后续资料都能归到正确的人名下。

    Acceptance Criteria:

  • [ ] 首次登录后引导创建本人档案。
  • [ ] 必填项尽量少，过敏史和长期疾病可选。
  • [ ] 完成后进入档案补全任务页。
  • [ ] 后续上传资料默认归属本人。

    • Priority: P0 | Effort: M | Dependencies: 成员模型

    Story 3：上传病历资料

    As a 患者本人，I want 上传病历、报告、处方、PDF 或照片，so that 我不用在各个医院网站和相册里反复查找。

    Acceptance Criteria:

  • [ ] 支持图片和 PDF 上传。
  • [ ] 上传后保存原始文件和文件哈希。
  • [ ] 用户可填写资料类型、医院、日期、科室、标签。
  • [ ] 上传失败、文件过大、格式不支持时有明确提示。

    • Priority: P0 | Effort: L | Dependencies: 文件存储、权限鉴权

    Story 4：手动分类归档

    As a 患者本人，I want 手动把资料分类归档，so that 即使没有 AI/OCR 也能形成可查的病历库。

    Acceptance Criteria:

  • [ ] 支持门诊记录、检查报告、处方、体检报告、其他资料。
  • [ ] 用户可修改分类和关联健康问题。
  • [ ] 保存后显示“已归档到谁的哪个分类”。
  • [ ] 每次修改保留审计记录。

    • Priority: P0 | Effort: M | Dependencies: 资料模型、审计

    Story 5：搜索和时间线

    As a 患者本人，I want 按关键词、医院、日期、类型搜索资料，并按时间线查看，so that 就诊前能快速找到相关材料。

    Acceptance Criteria:

  • [ ] 支持按成员筛选。
  • [ ] 支持关键词搜索标题、医院、备注。
  • [ ] 时间线按日期倒序展示。
  • [ ] 可按资料类型筛选。

    • Priority: P0 | Effort: M | Dependencies: 病历资料

    Story 6：添加当前用药

    As a 患者本人，I want 记录正在使用的药品和服药要求，so that 看病时能准确告诉医生当前用药。

    Acceptance Criteria:

  • [ ] 支持药品名称、规格、用途备注、用法用量原文。
  • [ ] 用法用量只能由用户填写或来自处方原文。
  • [ ] 支持开始日期、结束日期、停用。
  • [ ] 页面提示医记不提供用药建议。

    • Priority: P0 | Effort: M | Dependencies: 药品模型

    Story 7：用药提醒

    As a 患者本人，I want 为药品设置服药提醒，so that 我能按计划服药。

    Acceptance Criteria:

  • [ ] 用户可设置每天一次或多次提醒时间。
  • [ ] 用户可关闭提醒。
  • [ ] 提醒只基于用户输入，不自动推断剂量。
  • [ ] 今日页展示当天用药待办。

    • Priority: P0 | Effort: M | Dependencies: 待办/提醒

    Story 8：记录关键指标

    As a 患者本人，I want 记录血压、血糖、体重、心率、体温，so that 就诊前能展示近期状态。

    Acceptance Criteria:

  • [ ] 每条指标包含类型、数值、单位、日期、来源。
  • [ ] 来源可选手动记录、检查报告、体检报告、门诊记录。
  • [ ] 不自动判断异常或给出医学建议。
  • [ ] 可按时间查看历史记录。

    • Priority: P0 | Effort: M | Dependencies: 指标模型

    Story 9：待办事项

    As a 患者本人，I want 管理复查、用药和资料补全待办，so that 我知道下一步要处理什么。

    Acceptance Criteria:

  • [ ] 支持复查、用药、资料补全、资料核对类型。
  • [ ] 今日页展示优先级最高的待办。
  • [ ] 待办可完成、延期、取消。
  • [ ] 系统可创建资料缺失类待办，但不做医学判断。

    • Priority: P0 | Effort: M | Dependencies: 首页、资料、药品、指标

    Story 10：生成就诊资料包 PDF

    As a 患者本人，I want 就诊前选择相关资料并生成 PDF，so that 我可以直接交给医生查看。

    Acceptance Criteria:

  • [ ] 用户选择就诊成员和本次就诊目的。
  • [ ] 用户选择要包含的病历、指标和当前用药。
  • [ ] 用户填写近期情况和想问医生的问题。
  • [ ] PDF 包含本次目的、近期情况、相关资料列表、当前用药、关键指标、过敏史、原始资料索引。
  • [ ] 用户生成前可预览和核对。

    • Priority: P0 | Effort: L | Dependencies: 病历、药品、指标、PDF 导出

    Story 11：隐私授权

    As a 患者本人，I want 明确控制谁能看我的资料，so that 家庭管理不会侵犯我的隐私。

    Acceptance Criteria:

  • [ ] 敏感健康信息处理有单独同意记录。
  • [ ] 成年成员授权必须主动确认。
  • [ ] 默认客服和后台不能读取病历正文或原文件。
  • [ ] 撤销授权后立即失效。

    • Priority: P0 | Effort: L | Dependencies: 权限模型、审计

    Story 12：数据导出和删除

    As a 患者本人，I want 导出和删除我的资料，so that 我始终拥有数据控制权。

    Acceptance Criteria:

  • [ ] 用户可下载结构化数据和原始文件。
  • [ ] 用户可删除单份资料。
  • [ ] 用户可申请注销账号。
  • [ ] 删除过程撤销相关分享和会话。
  • [ ] 删除结果写入必要审计，不保留病历正文。

    • Priority: P0 | Effort: L | Dependencies: 文件存储、异步任务、审计

    五、数据指标与埋点方案

    医记数据指标与埋点方案

    版本：MVP Draft 日期：2026-07-10 原则：隐私优先、最小必要、只采集产品决策需要的数据

    1. 为什么需要埋点

    医记当前最需要回答的不是“用户点击了多少按钮”，而是这些业务问题：

    1. 用户是否能完成从注册到首份资料归档？
    2. 用户是否理解“手动整理 + 就诊资料包”的产品价值？
    3. 用户是否愿意持续维护病历、用药、指标和待办？
    4. 用户是否真的在就诊前生成资料包？
    5. 家庭成员和订阅是否带来增量价值？
    6. 哪些步骤让用户流失、失败或不信任？

    因此，MVP 埋点必须围绕业务闭环设计：

    
访问 -> 注册/登录 -> 本人建档 -> 上传资料 -> 分类归档
-> 添加药品/指标/待办 -> 搜索/时间线查看
-> 生成就诊资料包 -> 导出 PDF -> 留存/订阅

    2. 合规和隐私边界

    医疗健康信息属于敏感个人信息范畴。埋点不得采集病历正文、药品名称、诊断名称、检查结果原文、医院名称原文、文件名原文、邮箱明文、身份证号、手机号、原始文件 URL、分享 token、验证码、Cookie、访问令牌。

    埋点只允许采集以下类型：

    • 匿名或伪匿名用户 ID。
    • 成员数量、资料数量、药品数量、指标数量等计数。
    • 文件类型、资料类型、操作结果、耗时、错误码等产品行为数据。
    • 是否完成某步骤、是否开启提醒、是否导出 PDF 等布尔或枚举数据。
    • 经白名单处理的页面、功能、按钮、套餐类型。

    禁止采集字段

    CategoryExamplesRule 病历正文主诉、诊断、检查结论、医嘱原文禁止 药品敏感信息药品名称、剂量、用法用量原文禁止 原始资料信息文件名、文件 URL、图片/PDF 内容、分享 token禁止 直接身份标识邮箱明文、手机号、身份证号、姓名禁止 精确健康数值血压具体值、血糖具体值、体重具体值默认禁止；如确需分析，只采区间或是否填写 医院/医生医院名、科室名、医生名默认禁止；如确需分析，只采“是否填写”

    可采集替代字段

    NeedDo Not CollectCollect Instead 判断上传了什么资料文件名、报告内容record_type, file_mime_group, file_size_bucket 判断分类质量医院名、诊断名has_hospital, has_record_date, has_tags, required_fields_completed_count 判断用药功能使用药品名称、剂量medicine_created, has_reminder, schedule_frequency_bucket 判断指标功能使用具体血压/血糖值metric_type, has_value=true, source_type 判断资料包可用性PDF 内容visit_pack_sections_count, included_records_count, export_result

    参考边界：个人信息处理应有明确合理目的、与目的直接相关，并采取对个人权益影响最小的方式；医疗健康信息属于敏感个人信息，应按更高标准处理。正式上线前需由合规律师复核。

    3. 北极星指标

    North Star Metric

    每月生成过至少 1 次就诊资料包的活跃用户数。

    定义：

    
Monthly Visit-Pack Active Users =
在自然月内完成 visit_pack_export_succeeded >= 1 的去重用户数

    为什么不用“上传资料数”作为北极星：

  • 上传资料只是中间行为。
  • 医记的最终价值是就诊前可用，而不是存文件。
  • 资料包能同时验证资料整理、药品、指标、搜索、分类和 PDF 导出是否成立。

    • 10. Implementation Recommendations

    Client vs Server

    前端埋点适合采集：

  • 页面进入。
  • 表单开始。
  • 用户点击入口。
  • 前端校验失败。

    • 后端埋点必须采集：

  • 登录成功/失败。
  • 上传成功/失败。
  • 归档成功。
  • PDF 导出成功/失败。
  • 授权、撤销、删除、导出。
  • 支付/订阅。

    • 核心业务指标以后端事件为准，前端事件只能辅助分析流失。

    Event Pipeline

    MVP 可以先用数据库表或轻量事件表：

    
product_events
- id
- event_name
- user_id_hash
- anonymous_id
- session_id
- properties_json
- occurred_at
- received_at
- environment

    要求：

  • 所有 properties 进入白名单校验。
  • 丢弃禁止字段。
  • 对邮箱等身份标识只保存哈希或不保存。
  • 服务端补充 received_at。
  • 失败事件也要记录，但只记录错误码，不记录请求正文。

    11. QA Checklist for Analytics

  • [ ] 每个 P0 用户故事至少有 1 个成功事件和 1 个失败事件。
  • [ ] Activation Funnel 能从事件直接计算。
  • [ ] PDF 导出成功率能从后端事件直接计算。
  • [ ] 不采集病历正文、药品名称、诊断名称、指标具体值。
  • [ ] 搜索事件不采集原始搜索词。

  • [ ] Staging 和 Production 数据隔离。
  • [ ] 用户删除/注销后，分析数据只保留不可识别的聚合数据或按政策处理。

    13. Source Notes

    • 《中华人民共和国个人信息保护法》要求个人信息处理遵循合法、正当、必要、诚信原则，并限于实现处理目的的最小范围。
    • 中国网信网对敏感个人信息的解读明确提到医疗健康信息属于敏感个人信息。
    • 《网络数据安全管理条例》自 2025-01-01 起施行，正式公开服务前需要纳入数据安全和个人信息处理合规评估。

    Paper Tigers

  • “没有 AI 就没有价值”：不成立。当前核心价值是安全集中保存、快速查找和就诊前资料包。
  • “必须先做 App”：不成立。网页足够验证上传、整理、导出和订阅意愿。
  • “功能少用户不会付费”：未必。若资料包解决真实就诊痛点，家庭版仍可验证付费。

    • Elephants in the Room

    1. 旧版文档和原型里 AI/OCR 承诺较多，必须主动降级，否则用户预期会错位。
    2. “中国大陆用户”与现有 Vercel/Resend 等服务之间可能存在长期生产适配问题，需要明确当前只是验证还是公开商业化。
    3. 医疗健康数据合规成本高，不能等到用户量起来后再补权限、删除、审计和备案。

    Data Permission Baseline

    Principles

    • 默认拒绝。
    • 每份病历、药品、指标、待办、资料包都必须有 member_id。
    • 后端根据资源真实归属鉴权，不接受前端声明的成员归属。
    • 成年成员资料必须主动授权。
    • 客服和后台默认无权读取病历正文和原文件。
    • 删除、导出、授权、分享都必须写审计。
