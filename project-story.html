把看病前找资料的混乱，做成一个可登录、可归档、可导出资料包的线上产品。

医记面向患者本人。它不做诊断、不提供治疗或用药建议，也不承诺 OCR 识别效果。当前 MVP 只解决一个确定问题：把病历、处方、药品、指标和待办整理好，在就诊前生成一份可导出的 PDF 就诊资料包。

01 / 项目背景

资料不是没有，而是用的时候找不到

很多人的健康资料散在相册、微信、纸袋和各家医院 App 里。平时看起来都在，真正复诊时却很难马上拿出来。

医记不做医疗判断。它做的是更基础但高频的事：把资料放好、把药品记清、把看病前需要给医生看的信息整理出来。

患者本人优先先把“我自己的健康档案”闭环跑通，再扩展到家庭成员。
就诊资料包核心交付是一份就诊前可核对、可导出的 PDF。
不做医疗判断MVP 不提供诊断、治疗建议、用药建议或 OCR 识别承诺。
隐私可控制导出、删除、授权和审计从一开始作为产品能力设计。
02 / 真实痛点

我先确认了三个真实问题

用户不一定需要复杂系统，很多时候只需要在就诊前把关键资料快速整理好。

资料散

检查报告、处方、微信图片、PDF、纸质病历分散在不同地方。真正要看病时，用户很难快速找到。

药品乱

家里有哪些药、给谁用、还剩多少、什么时候过期，靠记忆很容易出错。

看病说不清

医生问起时间、检查、用药和症状变化时，用户经常只能现场翻手机。

03 / 产品方案

医记先做一个可靠的健康资料整理工具

MVP 的重点不是“大而全”，而是让患者本人能完成从上传资料到导出就诊资料包的完整闭环。

医记是什么

一个面向患者本人的健康资料整理工具，帮助用户保存病历、药品、指标和待办。

医记不是什么

不是 AI 医生，不提供诊断、治疗建议或用药推荐，所有医疗事实都来自用户录入或原始资料。

当前 MVP 做什么

登录后上传资料，手动分类归档，维护药品、指标和待办，并在就诊前生成 PDF 资料包。

病历上传 手动分类 搜索和时间线 用药提醒 指标记录 就诊资料包 PDF 数据导出 隐私授权
04 / 系统结构

从用户动作到数据落点，路径要清楚

健康资料很敏感，所以页面、API、数据库和文件存储各自承担清晰职责。

01 用户网页

让用户知道下一步做什么

把复杂流程拆成明确入口。

  • 邮箱登录
  • 上传并归档资料
  • 生成就诊资料包
02 后端 API

把操作变成可靠记录

处理身份、权限、导出和审计。

  • 身份校验
  • 权限隔离
  • 上传、导出和关键写操作审计
03 数据与文件

不同数据放在合适位置

敏感内容不进入分析埋点。

  • PostgreSQL 存结构化数据
  • Redis 存短期状态
  • Blob 存原始文件
05 / 前端

原生页面，先把核心流程跑顺

线上网页采用原生 HTML/CSS/JavaScript。选择原生实现，是为了在早期更快验证交互、文案和部署路径。

06 / 后端

后端负责权限、文件和可追溯

后端使用 NestJS + TypeScript，配合 Prisma 管理数据库，支撑登录、会话、家庭成员权限、资料、药品、指标、待办、资料包导出和关键写操作审计。

NestJSTypeScriptPrismaPDF 导出
  • 邮箱验证码登录：Resend 发验证码。
  • 文件长期保存：Vercel Blob 保存原始资料。
  • 权限隔离：本人、家庭成员、授权访问分开处理。
  • 数据分析：用埋点观察注册、建档、上传、归档和导出过程，判断用户在哪一步流失。

08 / 技术栈

技术选择服务于登录、权限、文件和导出

这里不堆名词，只解释每一层为什么和产品可信度有关。

层级使用技术通俗解释
前端页面HTML / CSS / JavaScript用户实际看到、点击和完成任务的界面。
后端服务NestJS 11 / TypeScript处理登录、权限、资料保存、PDF 导出等后端逻辑。
数据库PostgreSQL + Prisma保存用户、家庭成员、病历、药品、指标和提醒等结构化数据。
临时状态Redis保存验证码、会话这类有时效的数据。
文件存储Vercel Blob保存用户上传的图片、PDF 和原始资料。
邮件登录Resend给用户邮箱发送验证码，是短信资质不足时的上线替代方案。
部署Vercel + 自有域名把网站发布到线上，让别人可以真实访问和测试。
09 / 关键取舍

我没有把它做成“大而全”的医疗产品

这个项目最有价值的部分，不是页面数量，而是每一步都在处理“用户到底怎么用”和“上线后能不能负责”。

先整理，不诊断健康数据很敏感，所以产品边界定在保存、分类、提醒和导出。
先手动归档，再谈识别当前 MVP 不承诺 OCR 识别效果。先保证用户能可靠上传、分类、搜索和导出。
敏感内容不进埋点用漏斗衡量闭环，但不采集病历正文、诊断名、药品名、指标数值或文件 URL。
原型和正式网页分开原型展示设想；线上网页承接真实登录、数据保存和后端 API。
上线必须能被衡量用事件字典观察注册、建档、上传、归档、资料包和 PDF 导出。

11 / 项目历程

从原型到线上，再到可信和可衡量

这条时间线展示的不是“做完了”，而是一个产品如何不断收敛边界、补齐工程和上线条件。

第 1 阶段

产品原型

根据 PRD 做出网页版原型，确认医记不是医生工作台，而是给患者本人和家庭使用的记录工具。

第 2 阶段

交互打磨

调整首页、时间线、分类、药箱、指标趋势、就诊资料包和导出打印等页面，去掉不合适的医生视角。

第 3 阶段

后端搭建

搭建 NestJS API，接入 PostgreSQL、Redis、权限模型、文件上传、药品、指标、待办和资料包导出。

第 4 阶段

正式登录

由于短信资质限制，先改成邮箱验证码登录；接入 Resend，并完成域名 DNS 验证。

第 5 阶段

上线准备

绑定 yijijiankang.cn，加入隐私政策、服务协议、安全响应头、长期文件存储和生产环境检查。

下一步

从“可用”到“可信、可衡量”

继续补齐核心埋点、国内备案/合规评估、错误监控、付费意愿验证、文件删除恢复、后台运营和更稳定的国内通知通道。

医记项目复盘

它的重点不是替用户做医疗决定，而是把散落的资料整理成就诊前真正能用、能核对、能导出的信息。
